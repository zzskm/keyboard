## 2. 현황 진단

### 2.1 main이 어긋나 있다

`7b3c569`가 `tools/build_seam_v5.py`만 바꿨다(커버 윗면 Z 19 → 18.5, 창을 실루엣 윤곽으로 단순화). 생성물은 다시 만들지 않았다.

| 대상 | main의 상태 |
|---|---|
| 생성기 `build_seam_v5.py` | `v5_skirt_cover_H` 1.2 → 커버 윗면 Z 18.5, 두께 5.5, `v5_cover_silhouette_*` 매개변수 5개 추가 |
| `model/46es_mount_seam_v5.sc`, `parameters_seam_v5.csv` | `v5_skirt_cover_H` 1.7, 윗면 Z 19, 실루엣 매개변수 없음 (실측) |
| `print_v5/`, `review_v5/`, 검토 모델, 가이드, `design.md` 치수 표 | Z 19 기준 |
| `verify_seam_v5.py` | `v5_cover_top_Z == 19`, `TBD_cover_T == 6`, `NEW_PARAMS` 고정 목록. 재생성한 CAD에서는 실패한다 (판독) |
| `check_repository.py`, CI | 통과 (실측). 생성기 → CAD 고리를 기록하지도 검사하지도 않는다 |

현재 생성기는 빌드된다: `--probe`로 캐시에만 빌드해 Z 18.5·두께 5.5·오류 없음을 확인했다(실측, 작업 트리 변경 없음). 즉 다음 작업자가 mount만 고치려고 `build_seam_v5.py`를 실행해도 커버가 Z 18.5로 바뀐 CAD가 나오고 검증이 막힌다. [validation.md](validation.md)의 계획은 Z 18.5를 "첫 후보"로 두고 실측·시험 뒤 채택한다고 적었으며, `design.md` 결정 이력에는 기록이 없다.

원인은 두 가지다. 시험 변경이 브랜치가 아니라 main에 들어갔고, 그걸 잡을 검사가 없었다. 검토 모델은 `assembly_reference_v5.json`에 `generator_sha`를 남기지만 생산 CAD에는 같은 기록이 없다.

### 2.2 커밋마다 붙는 고정 비용

- **manifest.json**: 46es 커밋 69개 중 64개가 수정했다(실측). 절차는 `git add` → `update_manifest.py` → `git add manifest.json` → `--check` 네 단계이고 `--check`만 9.8 s 걸린다(실측, 파일 185개를 `git cat-file`로 하나씩 읽음). 내용은 **git 인덱스에서 계산한** 경로·크기·SHA-256·blob SHA라서 git 트리의 사본이다. git이 못 잡는 변경을 잡을 수 없고, 읽는 곳은 CI의 자기 검사뿐이다. 병행 브랜치는 전부 이 파일을 고치므로 병합 때마다 충돌한다.
- **결정 이력의 커밋 해시**: 결정 커밋 뒤에 "해시 기입"만 하는 후속 커밋이 3개(`d36b6c8`, `6115719`, `4b7ffc9`), 이력 재작성 뒤 해시 참조를 고친 커밋이 1개(`cae5fe9`) 있다. 후속 커밋마다 manifest 갱신과 push가 따라붙는다.
- **수동 명령 사슬**: AGENTS.md §10 기준 형상 변경 한 번에 생성·내보내기·검증 5개, 조립 검토 3개, stage·manifest·검사 6개, 게시 1개로 15개다. 어느 단계가 낡았는지는 사람이 기억한다. 같은 명령 목록이 AGENTS.md, validation.md, guide/README.md, model/README.md, README.md 다섯 곳에 있다.
- **환경 준비**: `PYTHONUTF8=1`을 매번 직접 설정해야 한다. SolidCraft CLI 경로가 7개 파일에 하드코딩돼 있고 `--cli`는 가이드만 받는다.
- **검증 JSON의 가짜 diff**: `verify_seam_v5.py`가 `set`을 순회해 dict를 만든다. `7b3c569`의 `seam-v5-verification.json` 변경은 키 순서뿐이었다(실측).

### 2.3 시간

전체 빌드 `build_seam_v5.py --probe` 2회 실측: 103 s, 91 s (SolidCraft 다른 세션이 떠 있는 상태).

| 구간 | 시간 | 비고 |
|---|---:|---|
| Python 준비 | 약 18 s | 실루엣 래스터 4.5 s, 브래킷 검사 1.9 s × 3 |
| CLI `run --save` | 39–41 s | 타임라인 695개 평가(204개는 억제) |
| CLI `eval` | 약 44 s | 방금 저장한 모델을 **다시 평가** |

평가 시간 구성(2026-11-09 캐시의 `eval_v5.json`, 합 33.4 s): CTRL 12.1 s, PLATE 11.8 s, MOUNT 2.1 s, COVER 1.9 s, REF 1.4 s, 기타 4.0 s. CTRL은 브래킷 B와 시험편 A·C를 같은 모델에서 세 번 만든다. PLATE는 v4 타임라인 끝에 붙인 join이 비싸다(뒤 다리 3개가 0.9–1.4 s씩).

- **재현되지 않는 바이트**: 같은 입력으로 두 번 빌드한 CAD의 SHA-256이 서로 달랐다(실측, seed도 다름: zip 타임스탬프). 하위 기록은 모두 CAD **파일** 해시에 묶여 있어(`source_sha256`, `v5_sha`, `model_sha`, 렌더 캐시 키) 형상이 같아도 다시 빌드하면 내보내기·벽 스캔·검증·검토 모델·렌더 20장이 전부 낡은 것으로 처리된다.
- **이중 내보내기**: `review_v5/`를 읽는 코드는 `verify_seam_v5.py`뿐이다. plate L/R과 커버 3개는 `review_v5`와 `print_v5/order2`로 두 번 내보내고 벽 스캔도 두 번 한다.
- **모델을 여러 번 연다**: 빌드 run, 빌드 eval, 검토 내보내기, 주문 2, 주문 1, 검증 eval, 검증 run이 각각 CLI를 띄워 8.8 MB 모델을 연다. 가이드는 렌더마다 10 MB 검토 모델을 연다.
- **캐시 구현 4종**: `cad_eval_cache.evaluation()`(해시 키), `build_seam_v5.evaluate()`, `build_guide.model_eval()`, `verify_seam_v5`의 수정 시각 비교·존재 여부 검사. 뒤의 방식은 체크아웃 순서에 따라 낡은 평가를 읽을 수 있다. tools 스크립트가 `guide/.cache/v5`에 쓰고, 정리하는 코드가 없어 `guide/.cache` 241 MB, `out` 69 MB, `out_publish` 47 MB가 쌓여 있다(실측).

정적 검사 `check_repository.py`는 5.6 s다(실측). 내보내기·검증·가이드 단계의 시간은 이번에 재지 않았다(추적 파일을 덮어쓰기 때문). 단계 2에서 계측한다.

### 2.4 구조

- **v4 기준 + 패치**: 생성기는 `baselines/seam_v4.sc`의 타임라인에서 204개를 억제하고 뒤에 피처를 붙인다. 피처 ID(7–11, 242–244)를 숫자로 참조한다. mount와 브래킷은 이미 처음부터 생성하는 구조로 옮겼고, plate·커버·spine이 v4 타임라인에 남아 있다.
- **검증 기대값이 리터럴**: `verify_seam_v5.py`에 Z 19, 두께 6, 살 3.9, 새 매개변수 목록, 바뀐 바디 집합, gate relief 부피 산술이 손으로 적혀 있다. 설계를 바꿀 때마다 검증기도 손으로 고쳐야 하고, 고치는 순간이 AGENTS.md §5가 경계하는 "통과시키려 기대값을 바꾸는" 지점과 구분되지 않는다.
- **기준 모델이 예외 산술로 유지된다**: `flat_Z18.sc`(9.4 MB)는 검증 전용인데, plate는 이미 "기준 대비 차이 = 뒤 다리 부피 + gate relief"로만 비교한다.
- **부품 표가 여러 곳에**: `export_print_v5.PARTS`·`TRIAL_PARTS`, `export_seam_v5_review.PARTS`, `verify_seam_v5.PRINT_SET_FILES`·`TRIAL_STL`, `guide_v5.json`의 printed, `print_v5/README.md` 표(크기·부피·최소 벽은 손으로 옮긴 값).
- **공통 코드 미분리**: `sha()` 정의 11곳, `write_text` 30곳 중 `newline` 지정 4곳(AGENTS.md §10이 경고하는 CRLF 해시 불일치의 원인).
- **CI**: Ubuntu에서 manifest와 정적 검사만 돈다. 의존성 버전을 고정하지 않았다. SolidCraft 없이 돌 수 있는 순수 Python 생성 논리(mount 윤곽, 브래킷 검사)는 검사하지 않는다.
- **저장소 용량**: 추적 중인 `.sc` 5개가 40 MB, `.git` 244 MB. 재생성할 때마다 8.8 MB + 10 MB가 새로 쌓인다.
