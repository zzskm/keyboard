# 46es 작업 지침

작성 기준: 2026-11-06. 적용 대상: `zzskm/keyboard/46es`의 설계·코드·제작 자료·조립 가이드 작업.

권장 저장 위치는 `46es/AGENTS.md`다. 이 문서를 그 위치에 둘 경우 별도 WORKFLOW 사본을 유지하지 않는다. 이 문서는 작업 방법을 정한다. 현재 설계 수치·재료·미해결 항목은 각 기준 문서에서 관리한다.

## 1. 먼저 현재 작업 상태를 확인한다

[README](README.md)와 [설계 문서](docs/design.md)에서 현행 모델을 확인하고, 실제 저장소의 브랜치·기준 커밋·미커밋 변경을 확인한다. 로컬 작업 완료, 원격 업로드, 병합, 가이드 게시, 제작 발주는 각각 기록한다. 과거 브랜치의 파일을 옮기기 전에 현행 입력과 의존성을 확인한다.

## 2. 작업 시작 시 여섯 가지를 고정한다

다음 항목을 확인하고 작업 설명에 짧게 적는다. 매번 새 계획 파일을 만들 필요는 없다.

1. **목적:** 이번 요청으로 무엇을 해결하는가.
2. **기준:** 브랜치·커밋과 사용할 설계 모델은 무엇인가.
3. **범위:** 문서, 파일 정리, 설계, 재료, 실측, 가이드 중 무엇을 바꾸는가.
4. **보존:** 키 배열·체결 구조 등 이번 요청이 바꾸지 않는 요구는 무엇인가.
5. **원본:** 어느 입력을 고치며 어떤 출력물이 따라 바뀌는가.
6. **완료 조건:** 어떤 검사·실물 확인·원격 반영까지 수행하는가.

일반적인 구현 선택과 되돌릴 수 있는 정리는 진행한다. 요구 해석에 따라 주요 구조·호환성·비용이 달라지는 선택만 사용자에게 확인한다. 이미 확정된 결정을 반복해서 묻지 않는다.

작업 예: “v5 커버 자석 포켓 위 살을 보강한다. 키 중심·plate 체결 구조는 유지한다. 생성 규칙을 수정하고 커버·연관 검토 모델·출력물·가이드를 갱신한다. CAD 벽·간격 검사를 수행하며 실제 흡착력은 실물 확인으로 남긴다.”

## 3. 결정과 근거를 구분한다

46es는 non-split 키보드다. plate나 mount를 분할 제작하는 것과 split keyboard는 다르다. 46sp는 별도 참고 예시다. r2 DWG는 기존 아크릴 버전의 원본이며 현재 3D 출력 설계와 동일한 구조라고 가정하지 않는다. 원본 자료(`cad/`, `firmware/`, `images/`)는 덮어쓰지 않는다. 재배포 조건을 확인하지 않은 외부 모델(예: Wilmore 케이스 STL)은 커밋하지 않는다.

| 정보 | 사용 방법 |
|---|---|
| 사용자 요구·명시적 결정 | 현재 작업의 제약으로 유지한다. 새 요구가 기존 결정을 바꾸면 해당 내용과 이유를 갱신한다 |
| 현물 측정 | 측정 대상·기준면·도구·범위·날짜를 함께 기록한다. 한 지점의 값을 전체 최솟값이나 정밀 실측으로 승격하지 않는다 |
| 기존 DWG·공식 부품 도면 | 대상 부품·버전·단위를 확인한 뒤 사용한다 |
| 외부 참고 모델·공칭값 | 가정 또는 참고값임을 명시한다. PSD60 실측값처럼 표시하지 않는다 |
| CAD 계산·검사 결과 | 해당 모델과 설정에서의 결과다. 실물 강도·끼움·배선 적합성까지 통과한 것으로 표현하지 않는다 |

문서가 충돌하면 파일명·날짜만 보고 결정하지 않는다. 최신 사용자 결정, 해당 결정이 반영된 커밋·모델, 검증 결과를 함께 확인한다. 큰 구조 변경을 뒷받침할 근거가 없으면 기존 요구를 유지하고 불명확한 부분만 확인한다.

실측 원본 JSON은 관찰 기록으로 보존한다. `measurements.csv`는 상태·채택 판단 표다. CSV만 수정해도 CAD가 바뀐다고 생각하지 않는다. 새 실측을 채택할 때는 생성기가 읽는 JSON 경로, 가이드의 입력 경로, 채택 판단과 검토 모델을 함께 갱신한다. 과거 관찰값은 새 측정으로 덮어쓰지 않는다.

## 4. 변경 종류에 맞는 원본을 편집한다

| 변경 종류 | 먼저 편집할 곳 | 함께 확인할 것 |
|---|---|---|
| v5 형상·매개변수 | `tools/build_seam_v5.py`의 생성 규칙 | 현행 CAD, 매개변수 CSV, 영향받는 시험물·출력물, 검토 CAD, 검증·가이드 |
| 시험 쿠폰 구조 | `model/samples/46es_sw_hole_sample.sc`와 재현 가능한 수정 절차 | 실제 부품의 층·홀·재료·출력 방향을 재현하는지 |
| 케이스·키캡 참고 형상 | `tools/build_assembly_reference_v5.py`와 근거 데이터 | 출력 부품을 의도치 않게 바꾸지 않았는지, 가정과 실측이 구분되는지 |
| 재료·색·구매품 | 제작 안내와 가이드의 재료·하드웨어 항목 | 벽·공차·접착·자석·쿠폰 조건에 미치는 영향 |
| 조립 설명·화면 | `guide/guide_v5.json`, `assembly_v5.json`, 관련 자산 | 실제 조립 순서, 수량, 부품 참조, 화면·저장 상태 |
| 파일 정리·문서 정합성 | 경로·참조·현행 문서 | 현재 기능·CAD·출력물 보존, 검사·재생성 경로 |

조립 설명은 글보다 그림을 우선한다. 배선·끼움·극성처럼 순서와 방향이 중요한 내용은 `guide/diagrams.py`로 생성 원본(CAD 생성 모듈·펌웨어 JSON)에서 그리고, 손으로 그린 그림이나 수치를 옮겨 적은 그림을 두지 않는다(사용자 결정 2026-11-09).

생성된 v5 CAD만 직접 고치고 끝내지 않는다. 다음 재생성에서 변경이 사라진다. GUI/MCP에서 탐색한 변경은 채택 시 재현 가능한 입력에 반영한다. 생성기에 반영할 수 없는 변경이면 자동 덮어쓰기를 막고 편집 원본과 재현 한계를 명시한다.

매개변수 CSV는 현재 CAD와 일치하는 내보내기 결과다. 독립 원본처럼 고쳐 두지 않는다. 검증 결과 JSON의 숫자나 `ok`를 손으로 바꿔 통과시키지 않는다.

내부 바디 이름의 `V1`, `V3`, `TBD`는 현재 코드가 참조하는 식별자일 수 있다. 이름만으로 구버전 또는 삭제 대상으로 판단하지 않는다. 외부 파일 정리와 내부 CAD 식별자 변경을 묶지 않는다.

## 5. 한 변경을 끝까지 연결한다

**기준 확인 → 원본 수정 → 영향받는 파생물 갱신 → 검증 → 현행 문서 갱신 → 미사용 파일 정리 → 커밋·반영** 순서로 처리한다.

- 문서 수정과 형상 변경을 분리해서 검토할 수 있게 한다. 파일 정리를 이유로 설계를 바꾸지 않는다.
- 형상을 바꾸기 전에 변경할 바디·치수와 보존할 바디·키 배치를 정한다.
- plate는 기준 부품이다. 끼움 오차를 plate 재출력으로 풀지 않는다. 슬롯·여유·희생 살은 mount·커버·브래킷·구매품 쪽에 두고, 조립 중 보정(줄질·심·와셔)도 plate를 건드리지 않게 정한다. 사용자 결정(2026-11-05)이며 근거는 출력 공차 ±0.3 mm·±0.4 %와 재주문마다 1–2주다.
- 변경한 치수는 연관 쿠폰·끼움 상대·조립 순서·하드웨어·가이드까지 추적한다.
- 같은 작업에서 생산 모델과 검토 모델이 서로 다른 버전을 설명하지 않게 한다.
- 치수 변경은 정상인데 기존 기대값 검사에 걸린다면, 먼저 요구와 계산 근거를 검토한다. 통과시키기 위해 기대값·비교 기준을 무조건 새 결과로 바꾸지 않는다.
- 계산이 실패하면 캐시·내보내기·모델 버전이 일치하는지 먼저 확인한다. 예전 결과 파일을 복사해 성공한 것처럼 만들지 않는다.

공통 함수는 버전별 검증 스크립트에서 분리한다. 필요한 캐시는 현재 입력으로 다시 만들 수 있어야 한다. 다른 작업자가 과거에 실행한 스크립트의 로컬 캐시가 있어야만 통과하는 절차를 두지 않는다.

새 버전 번호는 파일을 수정할 때마다 붙이지 않는다. 기존 주문·조립 호환성 또는 공식 설계 기준을 구분할 필요가 있을 때 올린다. 반복 실험은 작업 브랜치와 무시되는 임시 경로에서 수행하고, 채택 결과와 결정 이유만 현행 자료로 반영한다.

## 6. 검증 수준과 완료 범위를 일치시킨다

| 작업 | 필요한 확인 | 확인하지 못하는 것 |
|---|---|---|
| 문구·링크 수정 | 링크·경로·내용 정합성. 화면 문구를 바꾸면 해당 화면 확인 | 형상·실물 적합성 |
| 파일 이동·삭제·공통 코드 분리 | 의존성·명령 경로·해시·가이드 부품 참조. 보존 대상 CAD/출력 바이트 비교 | CAD 커널의 새 형상 계산 |
| 형상·치수 변경 | CAD 재생성, 피처 오류·스케치 상태, 변경/보존 바디 비교, 벽·간격·겹침, CSV 일치 | 실물 출력 오차·강도·조작감 |
| 출력물 재생성 | 연결 성분·비정상 모서리·부피·경계 크기·방향·재료·원본/출력 해시 | 제조사의 실제 출력 품질 |
| 조립에 영향이 있는 형상·체결·설명 변경 | 현행 CAD로 만든 가이드에서 변경 단계와 완성 상태를 시각 검토. 모델 해시·단계·캡처·판정을 기록 | 실제 배선과 조립 편의성 |
| 가이드 화면·3D 조작 변경 | 위 시각 검토와 데스크톱·모바일·3D 실패 대체 화면 확인 | 실제 배선과 조립 편의성 |
| 제작 적합성 | 같은 재료·조건의 쿠폰, 실제 하우징·스위치·키캡·나사·배선 시험 | 다른 재료나 변경된 설계의 자동 승인 |

검사는 변경 영향에 맞춰 수행한다. 문서만 바뀌었는데 모든 CAD를 재생성하지 않는다. 코드나 형상이 바뀌었다면 저장된 과거 `ok`만 읽고 새 검사를 통과했다고 보고하지 않는다.

조립에 영향이 있으면 [가이드 시각 검토](guide/README.md#시각-검토)를 마쳐야 해당 변경의 검증이 완료된다. 게시 자산을 재사용한 경우 `UI 미리보기`, 가이드 입력과 표시가 그대로인 정리는 `대상 없음`으로 기록한다. 실행하지 못한 검사는 `미실행`, 실물에서 확인할 항목은 `실물 확인 대기`로 남긴다. CAD가 없어도 가능한 정리·정적 검사는 완료한다. 결과 보고에서 `로컬 작업 완료`, `검증 완료 범위`, `원격 반영`, `게시`를 따로 표시한다.

## 7. 파일은 현재 역할이 있어야 남긴다

텍스트인지 바이너리인지와 무관하게 다음 기준을 적용한다.

| 처리 | 대상 |
|---|---|
| 유지 | 현재 편집 입력, 현행 제작 세트, 사용 중인 검증·생성 코드, 실제 참조되는 원본 근거·실측 |
| 제한적으로 유지 | 현재 생성·회귀 검증에 직접 필요한 기준 모델. 사용하는 코드와 이유를 명시한다 |
| 통합 | 여러 문서에 반복된 현행 사양·구매품·시험 절차. 주 문서 하나로 모으고 나머지는 참조한다 |
| Git 이력으로 전환 | 대체된 버전, 폐기안, 완료된 단계별 작업 로그, 중간 명령 덤프, 중복 사본 |
| Git에서 제외 | `.bak`, 임시 출력, 렌더 캐시, 로컬 빌드 폴더 |

삭제 전에는 코드 import·입력 경로·생성 명령·문서 링크·검사 기준을 확인한다. 아직 사용 중인 구버전 파일은 의존성을 옮기거나 공통 기능을 분리한 다음 정리한다. 중요한 요구·결정 이유·제작 기록이 그 파일에만 있으면 먼저 현행 문서에 필요한 내용만 옮긴다.

폴더를 `archive/`로 옮기는 것만으로 정리를 끝내지 않는다. 일상 작업에 필요 없는 파일은 현행 트리에서 제거하고 커밋으로 찾게 한다. 기존 Git 이력을 재작성하거나 삭제하지 않는다.

현행 문서의 역할은 다음으로 한정한다.

- `README.md`: 무엇이 현행이며 어디서 시작하는지.
- `AGENTS.md`: 작업 순서와 변경·검증·정리 규칙.
- `docs/design.md`: 현재 구조·채택 이유·가정.
- `docs/validation.md`: 미해결 항목·확인 방법·다음 작업.
- `model/print_v5/README.md`: 실제 제작 파일·재료·수량·시험 조건.
- `guide/README.md`: 가이드 생성·게시·검사 방법.

날짜별 작업 보고서, 인계 문서, 새 계획 문서를 습관적으로 추가하지 않는다. 이력은 커밋·PR에 남기고, 다음 작업자가 필요한 현재 정보는 해당 문서에 갱신한다.

## 8. 병합은 요구와 구조를 기준으로 한다

“내 브랜치가 최신” 또는 “이쪽 파일을 우선”이라는 이유로 반대편의 설계 개선을 통째로 폐기하지 않는다. 파일 충돌 해결과 설계 채택은 별개다.

병합 전 두 브랜치의 **요구·구조·실측·제작물 차이**를 확인한다. 독립 변경은 함께 보존한다. 양립할 수 없는 구조 변경만 선택 대상으로 올린다. 선택할 때 빠지는 기능과 재설계 범위를 구체적으로 적는다.

병합 후에는 사용자가 중요하게 정한 키 배열·mount 구성·plate 보호·분해 방식 등이 보존됐는지 확인한다. 삭제된 예전 파일을 복구하는 것과 현행 모델에 개선점이 유지되는 것은 같은 의미가 아니다. 현재 형상과 검증으로 판단한다.

Git 상태에 타 작업자의 변경이 있으면 덮어쓰지 않는다. 병행 작업은 각자 브랜치·작업 디렉터리를 사용하고, 동일 CAD와 생성물의 동시 편집을 피한다.

## 9. 제작·게시 결과를 고정한다

주문 1은 쿠폰·mount 시험, 주문 2는 시험 결과를 반영한 본 출력이다. 시험물은 대신하는 부품과 같은 재료·색·관련 치수를 사용한다. 본체 치수가 바뀌면 시험물이 여전히 그 조건을 재현하는지 확인한다.

발주할 때는 실제로 보낼 STL/STEP, 재료·색·수량, 원본 모델 커밋과 해시를 고정한다. 발주 후 해당 세트의 내용을 몰래 교체하지 않는다. 변경본은 별도 제작 리비전으로 구분하고, 발주본은 Git tag 또는 명시된 커밋에서 재현한다. 단순 검토 모델과 참고 하우징은 발주 세트에 넣지 않는다.

`model/review_v5`는 조립 좌표의 검토 출력물이다. `model/print_v5`는 제작 세트다. 파일명이 비슷하다고 서로 대신 사용하지 않는다. 시험물과 구매 할인 쿠폰도 문서에서 구분한다.

가이드 소스 수정, HTML 생성, Pages 저장소 반영, 실제 게시 확인은 각각 기록한다. 다른 저장소에 게시되는 가이드를 원본 저장소 커밋만으로 배포 완료라고 보고하지 않는다. 게시는 `guide/publish_guide.py`로 한다(빌드·브라우저 검사·Pages 반영·게시본 확인). 가이드에 영향이 있는 변경을 main에 병합하면 같은 작업에서 게시까지 한다(사용자 결정 2026-11-09). 발주·결제·병합·게시 여부는 요청 범위와 실제 성공 결과를 따른다.

## 10. 실행 명령과 종료 보고

아래 명령은 저장소 루트에서 실행한다. CAD 관련 명령에는 SolidCraft CLI(경로는 `SOLIDCRAFT_CLI` 또는 기본 설치 경로)와 `46es/requirements.txt`의 Python 패키지가 필요하다. 가이드 브라우저 검사에는 Playwright가 필요하다. 변경 유형에 따라 §6의 검증 범위를 적용한다.

```sh
# 형상 변경: 원본 → 검토·제작 출력 → 형상 검사
python 46es/tools/build_seam_v5.py
python 46es/tools/export_seam_v5_review.py
python 46es/tools/export_print_v5.py
python 46es/tools/export_print_v5.py --trial
python -B 46es/inspection/scripts/verify_seam_v5.py

# 조립 검토 모델 → 검사 → 가이드
python 46es/tools/build_assembly_reference_v5.py
python -B 46es/inspection/scripts/verify_assembly_reference_v5.py
python -B 46es/guide/review_guide.py --steps standoff trial module --views reset iso

# 변경을 검토·stage한 뒤 마무리(정적 검사·스모크·공백·작성자·보고 틀)
# 아래 git add는 이번 작업의 46es 변경만 있을 때 사용한다.
git add 46es
python -B 46es/tools/finish.py

# main 병합·push 뒤 가이드 게시(가이드 영향이 있을 때)
python 46es/guide/publish_guide.py
```

다른 작업의 변경이 섞였으면 파일을 지정해 stage한다. `finish.py`는 stage 범위를 보여 주고 `check_repository.py`(의도한 커밋의 추적 파일 기준), `smoke_test.py`, `git diff --cached --check`, 저장소 로컬 작성자 확인을 차례로 실행한 뒤 아래 보고 틀을 출력한다. 생성 기록의 해시가 다르면 원본 변경·입력 경로·LF/CRLF부터 확인한다. 원인을 확인하지 않고 메타데이터만 덮어쓰지 않는다. 형상이 바뀌지 않는 생성기 정리는 `build_seam_v5.py --refresh-record`로 기록만 갱신한다(다시 빌드한 CAD가 커밋된 CAD와 바디 단위로 같을 때만 통과).

이전 결정을 뒤집는 형상 변경은 커밋 제목을 `decision:`으로 시작하고, [결정 이력](docs/design.md#결정-이력)의 커밋 칸에는 해시 대신 그 커밋 제목을 적는다(같은 커밋에서 쓸 수 있어 해시 기입용 후속 커밋이 필요 없다). 조회는 `git log --grep "^decision:" -- 46es`.

공통 경로·CLI·해시·JSON 쓰기는 `tools/common.py`를 쓴다. 이 모듈을 import하면 콘솔 출력이 UTF-8로 바뀌므로 `PYTHONUTF8=1`은 필요 없다(이 모듈을 쓰지 않는 옛 분석 스크립트는 여전히 필요할 수 있다). 기록 JSON은 `write_json()`으로 LF·고정 순서로 쓴다. 같은 입력으로 다시 실행했을 때 diff가 생기면 `set` 순회처럼 순서가 정해지지 않은 곳을 고친다. 텍스트 원본을 스크립트로 고칠 때는 `newline='\n'` 또는 `write_bytes`로 LF를 유지한다. 생성기·검사가 작업 트리 원본의 해시를 기록하므로(예: `generator_sha`), CRLF로 저장한 원본은 커밋된 LF 파일과 해시가 어긋난다.

작업 종료 보고는 다음 다섯 줄이면 충분하다.

```text
변경: 무엇을 해결했고 어떤 파일이 현행인가.
검증: 실제 실행한 검사와 결과.
남은 항목: 미실행 검사 또는 실물 확인.
반영: 로컬 커밋 / 원격 브랜치 / PR / main / 게시 상태.
다음 행동: 다음 작업자가 바로 수행할 한 가지.
```

업로드·권한·도구 문제로 막히면 가능한 로컬 작업을 완료하고, 실패한 단계와 오류를 즉시 알린다. 원격 반영을 끝없이 재시도하며 작업 상태를 불명확하게 두지 않는다. 필요하면 검증된 bundle 등으로 결과를 전달하고 미반영 상태를 명시한다.
